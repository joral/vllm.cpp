## 2. #2818: the blocker its own preamble warns about is GONE

#2818's "READ THIS BEFORE YOU SPEND THE LEASE" section says a source-built
oracle at this pin is refused on `vllm_distribution_version` before
`online_gate.py` reaches the commit assertion or the FlashInfer gate, after a
94-minute build. **That is no longer true, and it was checked in three ways
rather than read once.**

1. **The record moved.** `5d97007c2` (#2896, developer instruction) corrected the
   ` ```parity-pin ` block from `0.28.1rc1.dev132+ge126687a9.precompiled` to
   `0.28.1rc1.dev132+ge126687a9`. `.agents/upstream-sync.md` today carries the
   suffix-free value. The rationale is in the block's own prose: on aarch64
   `VLLM_USE_PRECOMPILED=1` leaves a 13,872-byte editable install with no
   compiled extensions, so the only mode whose string matched could not execute a
   kernel while the only mode that can execute was refused.
2. **The test that pinned the two strings as different was repaired.**
   `d45887e12` (#2931) replaced
   `test_metadata_and_runtime_strings_differ_on_the_pin` with
   `test_metadata_and_runtime_are_compared_as_two_independent_fields`, which
   keeps the `startswith` relation, adds two non-empty checks, and holds in both
   build regimes. The old assertion would have redded every source build forever.
3. **A second build measured the string independently.** Job `7386f034` read
   `importlib.metadata` from a directory that is not the source tree — the exact
   reading #2818's item 1 asks a lease to take — and printed
   `VLLM_VERSION 0.28.1rc1.dev132+ge126687a9`. Second device, second build, no
   suffix. The runhalf value the correction was taken from was a Thor build; this
   is GB10.

#2818's item 3 is also partly answered from the same log: the target's
**FlashInfer `0.6.18`** was observed in use on GB10, not inferred — the autotune
cache path is `/root/.cache/vllm/flashinfer_autotune_cache/0.6.18/121a/…` — and
`REVCOUNT=20591` was reproduced on the deep clone, so the shallow-clone hazard
(#1185) did not fire on this build either.

**One estimate in the recipe is now known to be low.** `2026-09-03-e126687-step6.md`

### 2.2 C1c: the warmup does not abort engine start on GB10, and that is one of its two questions

C1c asks two things. The log answers the first, narrowly, and does not touch the
second.

**Question 1, whether the `4.6.2` warmup compile succeeds on GB10 at all.** The
`kernel_warmup` block ran on a device at compute capability 12.1 and did not
fault:

```
INFO 09-04 12:44:13 [kernel_warmup.py:124] JIT kernel warmup starting.
INFO 09-04 12:44:13 [kernel_warmup.py:134] JIT kernel warmup finished in 0.00s.
```

and the engine reached the model and produced tokens after it. The
`has_device_capability(90)` gate #2818 names at `kernel_warmup.py:125-126` sits
between those two lines; the identification is by module and by adjacency in the
emitted line numbers, and this session did not read the pinned vLLM source to
confirm it, because doing so needs the tree the leased build had.

**This is a weak instance of the question and must not be read as more.** The
model is `facebook/opt-125m`: dense, unquantized, bf16, `enforce_eager=True`,
single GPU. The engine's own config line shows `enable_cutedsl_warmup=True`, so
the knob was on, but a 125M dense decoder reaches no MoE router GEMM, and the
`Warming up ll_bf16 router GEMM kernels.` line §7 asks for **did not appear** —
zero occurrences against a positive control of four `kernel_warmup` hits in the
same file, so the search shape is not the reason for the zero. `0.00 s` here is
therefore evidence that the path is entered and survives on `sm_121`, not
evidence about what it costs on the NVFP4 checkpoints the startup row measures.

**Question 2, what fraction of the oracle's 182.41 s startup the CuteDSL warmup
is, is untouched.** Nothing here measures a startup ratio. One adjacent
observation is worth carrying to whoever takes the lease, and it is a candidate
rather than a result: **FlashInfer autotune took ~58.6 s** on this trivial model
(`12:44:13,914` to `12:45:12,481`) and saved **0 configs**. On a 182.41 s
denominator that is a third of the budget from a function that is not CuteDSL
warmup, so the startup row's decomposition should measure both rather than
attribute the whole to one.

**The `nvidia-cutlass-dsl` version in the leased environment was not recorded.**
The log names no version for it. §3.4's two un-examined entry points,
`cutedsl_warmup()` and `fa4_cutedsl_warmup()`, are still un-examined.
